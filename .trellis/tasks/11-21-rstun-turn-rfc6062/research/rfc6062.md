# Research: RFC 6062（TURN TCP allocation）

- **Query**: 为 RFC 6062（TURN TCP allocation）实现做调研：方法集、Allocate 形态、Connect、ConnectionBind、ConnectionAttempt、生命周期、代码耦合点、验收路径、风险
- **Scope**: mixed（RFC 原文 + 本仓代码 + coturn 4.6.1 黑盒对照实测）
- **Date**: 2026-11-21
- **RFC**: <https://www.rfc-editor.org/rfc/rfc6062.txt>（Standards Track, 2010-11）
- **实验环境**: `/tmp/opencode/rfc6062-lab/`（coturn 4.6.1 `turnserver`、`turnutils_uclient`、python3 自写 STUN/TURN 探针 `probe.py`，未修改本仓任何文件）

> **一句话结论**：RFC 6062 的规范面很小（3 个方法码 + 1 个属性 + 2 个错误码），但**工程面很大**：
> 它把「一次 allocation 一个 UDP socket」变成「一次 allocation = 一个 TCP listener + N 条
> 双向字节流 + 一张 CONNECTION-ID 映射表」，而本仓当前的 allocation/回收/指标模型全部
> 假设「relay = 一个 `UdpSocket`」（`src/turn.rs:456`）。

## 1. 方法集与属性（RFC §6）

### 1.1 方法码（RFC 6062 §6.1）

| 方法 | 码 | 类 | 方向 |
|---|---|---|---|
| `Connect` | `0x00a` | Request / Success / Error | 客户端 → 服务器（**控制连接**上） |
| `ConnectionBind` | `0x00b` | Request / Success / Error | 客户端 → 服务器（**新建的数据连接**上） |
| `ConnectionAttempt` | `0x00c` | **Indication** | 服务器 → 客户端（控制连接上） |

### 1.2 新属性（RFC 6062 §6.2 / §6.2.1）

- `CONNECTION-ID = 0x002a`，**32-bit unsigned**，唯一标识一条 **peer data connection**。
  - 出现在：`Connect` 成功响应、`ConnectionAttempt` indication、`ConnectionBind` 请求。
  - **不出现**在 `Allocate` 响应（见 §2）。

### 1.3 新错误码（RFC 6062 §6.3）

- `446 Connection Already Exists`
- `447 Connection Timeout or Failure`

### 1.4 各消息必备属性（规范原文归纳）

| 消息 | 必备 | 可选/说明 |
|---|---|---|
| `Allocate`(6) | `REQUESTED-TRANSPORT=6`；`LIFETIME` MAY | **MUST NOT** 带 `DONT-FRAGMENT` / `RESERVATION-TOKEN` / `EVEN-PORT`（§4.1） |
| `Allocate` 成功 | `XOR-RELAYED-ADDRESS`（TCP 地址） | `XOR-MAPPED-ADDRESS`（RFC 5766 §6.2 要求）、`LIFETIME`；**MUST NOT** 带 `RESERVATION-TOKEN`（§5.1 第 5 条） |
| `Connect` | `XOR-PEER-ADDRESS` | — |
| `Connect` 成功 | `CONNECTION-ID` | — |
| `ConnectionBind` | `CONNECTION-ID` | 无其他 TURN 属性；新连接走**同一鉴权**（§4.3） |
| `ConnectionAttempt` | `CONNECTION-ID` + `XOR-PEER-ADDRESS` | indication，无 MI（RFC 5389 indication 不带完整性） |

**线上抓包核对**（coturn，见 §10 原始证据）：
```
Allocate ok  len=88  XOR-RELAYED-ADDRESS, XOR-MAPPED-ADDRESS, LIFETIME, SOFTWARE, MESSAGE-INTEGRITY, FINGERPRINT
Connect  ok  len=32  CONNECTION-ID(0x002a)=1050458123, MESSAGE-INTEGRITY
ConnectionAttempt ind len=52  CONNECTION-ID=18732569, XOR-PEER-ADDRESS, SOFTWARE, FINGERPRINT
ConnectionBind req len=88  CONNECTION-ID, USERNAME, NONCE, REALM, MESSAGE-INTEGRITY, FINGERPRINT
ConnectionBind ok  len=56  SOFTWARE, MESSAGE-INTEGRITY, FINGERPRINT
```

> 注意 two 个 coturn 细节（非 RFC 义务，但影响「逐字节对照」口径）：
> 1. `Connect` 成功响应**不带 `SOFTWARE`**（len=32）；
> 2. `ConnectionAttempt` indication 带 `SOFTWARE` 与 `FINGERPRINT`。

## 2. Allocate 的 TCP 形态（RFC §5.1）

### 2.1 服务端处理（RFC 6062 §5.1，对 RFC 5766 §6.2 的增量）

1. `REQUESTED-TRANSPORT` 既非 UDP 也非 TCP → `442`；UDP → 走 RFC 5766；UDP 但本地策略禁用 → `403`。
2. **客户端连接传输不是 TCP/TLS → `400 Bad Request`**（即 UDP 控制连接上申请 TCP allocation 必须是 400）。
3. 带 `DONT-FRAGMENT`/`EVEN-PORT`/`RESERVATION-TOKEN` → `400`。
4. 分配 **TCP** 中继地址（而不是 UDP）。
5. 成功响应 **MUST NOT** 带 `RESERVATION-TOKEN`。

### 2.2 与 UDP allocation 的差异

| 维度 | UDP allocation（现状） | TCP allocation（RFC 6062） |
|---|---|---|
| 中继套接字 | `Arc<UdpSocket>`，`take_port` 里 `udp_socket()`（`src/turn.rs:668`） | TCP **listener**（`ss -ltn` 可见，实测见 §10.6） |
| 数据面 | `Send`/`Data` indication 或 `ChannelData`（STUN 封装） | **裸字节流**，按 `CONNECTION-ID` 一一配对 |
| 每 peer 一连接？ | 否，一个 relay 端口对任意多 peer（permission 表控制） | **是**，「每个 peer transport address 每 allocation 最多一条」（§3 Note） |
| `CONNECTION-ID` | 无 | `Connect` 成功后分配 |
| 控制面要求 | 任意（UDP/TCP/TLS/DTLS） | **必须 TCP 或 TLS**（§4.1、§5.1 第 2 条） |
| `DONT-FRAGMENT`/`EVEN-PORT` | 支持 / 支持 | 请求出现即 `400` |

### 2.3 PRD 的一处表述需要纠正

`prd.md` 范围第 1 条写「成功返回 200 + `XOR-RELAYED-ADDRESS` + **`CONNECTION-ID`**」。
**RFC 没有这条**：§5.1 的增量清单里没有任何 `CONNECTION-ID`；`CONNECTION-ID` 只在
`Connect` 成功（§5.2）与 `ConnectionAttempt`（§5.3）里出现。coturn 实测的 `Allocate ok`
也确实只有 `XOR-RELAYED-ADDRESS / XOR-MAPPED-ADDRESS / LIFETIME / SOFTWARE / MI / FINGERPRINT`。

- 若按 PRD 实现（Allocate 带 `CONNECTION-ID`），coturn 客户端不会理解，且与「逐字节对照 coturn」冲突；
- 建议 design 阶段把 PRD 该条改为「Allocate 只返回 TCP 中继地址；`CONNECTION-ID` 由 `Connect`/`ConnectionAttempt` 产生」。

### 2.4 当前实现（现状，非建议）

`src/turn.rs:976-996`：`requested[0] == TRANSPORT_TCP` 直接回 `442`，**在检查客户端传输之前**。
因此今天在 UDP 控制连接上申请 TCP allocation 得到的是 `442`，而 RFC 6062 §5.1 第 2 条要求 `400`。
实测（本仓 26.410.103，`--tcp --turn`）：
```
rstun Allocate(TCP) over TCP -> 442
rstun Allocate(TCP) over UDP -> 401（未鉴权）→ 鉴权后 442
```
coturn 同一场景：`400 Wrong Transport Data`。

## 3. `Connect`（RFC §5.2）

### 3.1 处理顺序（规范原文，逐条）

1. 该 TCP 连接上没有 allocation → `437 Allocation Mismatch`。
2. 同一 allocation 正在处理同一 `XOR-PEER-ADDRESS` 的 `Connect` → `446`。
3. 同一 allocation 已成功 `Connect` 过同一 `XOR-PEER-ADDRESS`，且数据连接 pending/active → `446`。
4. 缺 `XOR-PEER-ADDRESS` 或值非法 → `400`。
5. 本地策略禁止 → `403`。
6. 否则服务器发起出站 TCP：**本地端点 = 该 allocation 的中继地址**，远端 = `XOR-PEER-ADDRESS`。
   失败或超时 → `447`；**超时值 MUST ≥ 30 秒**。
7. 成功 → 该连接称为 **peer data connection**；服务器**缓冲**从客户端收到的数据（在 bind 之前），
   并按缓冲余量调整通告的 TCP 接收窗口。
8. 成功响应 MUST 带 `CONNECTION-ID`，其值唯一标识该 peer data connection。
9. **30 秒内没有对应 `ConnectionBind` → MUST 关闭 peer data connection**。

### 3.2 与 `CreatePermission` 的关系（关键取舍点）

- 规范：`Connect` 一节**没有**任何 permission 检查；permission 只在 §5.3（**入站**）要求。
- 实测（coturn 4.6.1）：不发 `CreatePermission` 直接 `Connect` → **`200` + `CONNECTION-ID`**，
  且对端看到的来源地址就是中继端口：
  ```
  Connect WITHOUT CreatePermission: Connect ok cid= 2759696134
  peer accepted connection from ('127.0.0.1', 49791)   ← 49791 就是 relayed address
  ```
- 但 `turnutils_uclient -T`（`-y` 客户端对客户端）会先发 `CreatePermission` 再 `Connect`；
  `-T -I`（不装 permission）实测失败：`tcp connect sent` → `connection bind sent` → `recv: Connection reset by peer`
  （失败点在**对端那一侧**的入站连接：对端没有 permission，被服务器立即关闭 → 本端 bind 无对象）。
- 结论：**出站 `Connect` 不需要 permission；入站（被动）需要**。这两条必须分开实现与测试。

### 3.3 实测到的错误码（coturn 4.6.1）

| 场景 | 结果 | 备注 |
|---|---|---|
| 连 127.0.0.1 上已关闭端口 | `447`（0.00 s） | ECONNREFUSED 立即失败 |
| 同一 peer 重复 `Connect`（第一条已 active） | `446` | 与规范一致 |
| 无 `CreatePermission` | `200` | 与规范一致（coturn 不额外要求） |
| 连 `10.255.255.1:12345`（本机 loopback 源无路由） | `500`，日志 `Server error: TCP relay socket for connection cannot be created` | coturn 把「中继 socket 建不出来」归为 500，非 447 |
| 连「SYN 被丢弃」的对端（accept 队列塞满） | `447`，**19.4 s** | **低于 RFC 的 30 s 下限**；无法区分是 coturn 自设超时还是内核 connect 超时 |

> 对本仓的含义：`447` 的语义是「连接失败**或**超时」；`500` 属于「中继 socket 无法创建」。
> 实现时要明确「建 socket 失败」算 500 还是 447——RFC 只说「connection attempt fails → 447」。

## 4. `ConnectionBind`（RFC §5.4 + §4.3/§4.4）

### 4.1 客户端侧要求（§4.3）

- 收到 `Connect` 成功后，**新建一条到同一服务器地址的 TCP 连接**，且**必须使用不同的本地传输地址**；
- 新连接用**与控制连接相同的鉴权方式与凭据**；
- 在新连接上发 `ConnectionBind`，`CONNECTION-ID` 原样回显；
- 成功响应的那条连接即 **client data connection**。

### 4.2 服务端侧处理（§5.4）

1. 客户端连接传输不是 TCP/TLS → `400`。
2. 缺 `CONNECTION-ID`，或该值不指向**存在的 pending 连接** → `400`。
3. 否则该连接成为 client data connection：双向**原样转发**，包括「`Connect` 成功之后、
   `ConnectionBind` 之前」已经从 peer 收到的数据（**必须预缓冲**）。

### 4.3 绑定后是否还解析 STUN

**不解析。** §3 原文：「after an initial TURN message that binds the client data connection to a
peer data connection, **only application data** can be sent -- no TURN messaging」。
实测证据（对 coturn）：

```
ConnectionBind ok → 紧接着双向任意字节：
  data conn recv: b'peer->client'
  peer recv:     b'client->peer'
```

本仓自写的解析器在 bind 之后继续按 STUN 解析，得到的是 `0x0 req len=0` / `0x187 ok len=1799`
这类垃圾帧——**这正是「裸字节」的直接证据**（见 §10.2 输出）。

### 4.4 错误码实测（coturn 4.6.1）

| 场景 | 规范 | coturn 线上 | coturn 日志 |
|---|---|---|---|
| 错 `CONNECTION-ID` | `400` | **无响应**：直接 RST（客户端 `ConnectionResetError`，收到 0 字节） | `CONNECTION_BIND processed, error 400: Wrong connection id` |
| 同一 ID 第二次 bind（第三条连接） | 规范未明说（ID 已被消耗） | 同上：RST，0 字节 | 同上 |
| `Connect` 后 >30 s 才 bind | `400`（pending 已关闭） | 同上：RST，0 字节 | `Wrong connection id` |

**结论**：coturn *记录* 400 但**不把它发到线上**（写完立即销毁连接 → RST 抹掉缓冲）。
本仓若按 RFC 发 `400` 再关连接，是**比 coturn 更规范**的行为；对照测试要用「我方发 400 /
coturn 只 RST」的显式差异判定，不能做逐字节 diff。

### 4.5 5 元组如何记录

- 控制连接：5 元组 = (client, transport=Tcp|Tls, server)，即本仓现有 `Key`（`src/turn.rs:363-368`）。
- 数据连接：**不占用 allocation 的 5 元组**（它是另一条 TCP 连接的 5 元组）。
  需要一张独立的映射：`CONNECTION-ID (u32) → { peer_addr, peer_stream, pending|bound, allocation_ref }`，
  数据连接自身按「accept 时的 5 元组」找到它绑定的那条 entry（或直接把 stream 交给该 entry）。
- 实测（coturn 日志）：数据连接在 coturn 里是**独立 session id**（如 `029000000000000002`），
  与控制的 `001000000000000002` 不同——印证「数据连接不在 allocation 主表里」。

## 5. `ConnectionAttempt`（被动模式，RFC §5.3 + §4.4）

### 5.1 触发条件与服务端行为

1. 在中继地址上收到入站 TCP 连接 → MUST accept（accept 失败则什么都不发给客户端）。
2. accept 成功即 peer data connection；MUST 缓冲 peer 数据。
3. **该 peer 没有 permission → accept 后立即关闭**（不通知客户端）。
4. 有 permission → 控制连接发 `ConnectionAttempt`，带 `XOR-PEER-ADDRESS` + `CONNECTION-ID`。
5. 30 s 内没有 `ConnectionBind` → 关闭 peer data connection。

实测：
```
有 permission：peer 连 relay → 控制连接收到 ConnectionAttempt ind cid=3171518745 → bind ok → 双向数据通
无 permission：peer 连 relay → RST（ConnectionResetError），控制连接 5 s 内无任何 indication
```

### 5.2 coturn 支持度

- 支持，且 `turnutils_uclient -P` 就能触发（`-P` 蕴含 `-T`）。
- `-P` 实测抓包序列（无 `Connect` 方法）：
  ```
  Allocate(TCP) ok → CreatePermission ok → ConnectionAttempt ind(CONNECTION-ID=2641776650)
  → [新连接] ConnectionBind req(CONNECTION-ID=2641776650) → ok → 裸字节
  ```
- 注意 `-P` 实测有丢包：`tot_send_msgs=6, tot_recv_msgs=3`，`Total lost packets 3 (50%)`，
  但 `uclient_ok` 判据（`lost packets 0`）仍要求 0 —— 若把 `-P` 纳入 lab，
  **不能**直接复用 `uclient_ok`（`script/lab/rstun-turn.sh:202`）。

### 5.3 规范对被动模式的隐含工作量

被动模式需要的额外件：accept 循环（每 allocation 一个 listener 任务）、
permission 检查、`ConnectionAttempt` 的 indication 生成与**发送到控制连接**（控制连接可能是
UDP/TCP/TLS/DTLS 四种之一，且 indication 必须走该连接的 sink）、以及「未 bind 的 30 s 计时器」。

### 5.4 是否建议本期实现：**建议不纳入本期（P2 二期内部再切一刀）**

理由（只陈述事实与代价，取舍由 design 决定）：

1. **`-T` 已覆盖 RFC 6062 的主用例**：PRD 的动机是「企业网络阻断 UDP，TCP 中继可用」；
   这靠出站 `Connect` + `ConnectionBind` 就成立，`-P` 只是「对端主动连我」的场景。
2. **被动模式要求把 `ConnectionAttempt` 送到控制连接的 sink**，而控制连接可以是
   UDP/TCP/TLS/DTLS；出站模式完全不需要「服务器主动向控制连接推消息」，
   这条路径今天在 `src/turn.rs` 里**不存在**（只有 `spawn_relay_reader` 向 sink 推 relay 数据）。
   即：被动模式新增的是「allocation → 控制连接」的反向通道，而不是复用现有通道。
3. **验收判据不稳**：coturn + `uclient -P` 实测 50% 丢包，`uclient_ok` 的 `lost packets 0`
   判据不可直接复用，需要新的判定口径（这笔成本与「实现被动模式」本身无关，但会拖慢验收）。
4. 反过来：不实现被动模式时，`ConnectionAttempt（0x00c）` 可以完全不做，
   `permission` 只需在 `Connect` 侧**不**检查（少一张表的分支）。

> 若 design 决定纳入：建议顺序仍是先 `-T` 全绿（含 446/447/400/半开/回收），再加被动模式，
> 因为两者共享 `CONNECTION-ID` 表与 bind 状态机，只有「谁来发起」不同。

## 6. 生命周期与回收

### 6.1 规范要求

| 项 | 要求 | 出处 |
|---|---|---|
| `Refresh` | 与 UDP 完全相同；**MUST 在控制连接上发** | §4.2、§5.1 |
| `LIFETIME` | 语义与 UDP 相同（`Allocate` MAY 带；`Refresh` 续期） | §4.1、§4.2 |
| allocation 过期 | **MUST 关闭该 allocation 的所有数据连接** | §5.5 |
| client data connection 关闭 | **MUST 关闭对应 peer data connection** | §5.5 |
| peer data connection 关闭 | **MUST 关闭对应 client data connection** | §5.5 |
| 未 bind 的 pending 连接 | 30 s 后 **MUST** 关闭（`Connect` 与入站两条路径都适用） | §5.2、§5.3 |
| 预绑定缓冲 | 服务器 MUST 缓冲；缓冲将超本地策略上限时**允许直接丢弃连接**（防内存耗尽） | §5.2、§5.3、§7 |
| 流控 | 「写不动就停止读源」端到端背压 | §3 末段 |
| 保活 | **不提供** NAT 保活；TCP keep-alive MAY，属于应用层 | §4.6 Note |
| 配额 | RFC 6062 不新增；沿用 RFC 8656 的 `486 Allocation Quota Reached` | RFC 8656 §7.2 |

### 6.2 `LIFETIME=0` 实测（coturn 4.6.1）

```
Refresh LIFETIME=0 -> ok
  peer read       -> ConnectionResetError
  data-conn read  -> ConnectionResetError
  control conn    -> ConnectionResetError
coturn 日志：closed (2nd stage) ... reason: allocation timeout
```

即 coturn 在 `LIFETIME=0` 时**连控制连接一起关**。RFC 只要求关数据连接（§5.5）；
控制连接是否保留由实现决定——本仓现状是 `LIFETIME=0` **只**删 allocation、**保留控制连接**
（`src/turn.rs:1458-1471`）。design 需要明确 TCP allocation 版的取舍。

### 6.3 本仓现状（现状描述）

- 过期回收靠 **1 秒扫描器** `Turn::sweep`（`src/turn.rs:725-762`，`start_sweeper` 764-775）；
  移除 `Allocation` 时 `Drop` abort `relay_task`（`src/turn.rs:500-505`），socket 随之释放。
- 控制连接关闭时 `release_connection` 立刻删 allocation（`src/turn.rs:637-651`，
  调用点 `src/main.rs:2806`、`3431`）——注释说明理由是「writer task 已死，留到 TTL 只会泄漏 relay socket」。
- 权限：`permissions: HashMap<IpAddr, Instant>`，5 分钟 TTL，上限 `permission_limit`（默认 10），
  超限 `508`（`src/turn.rs:1562-1591`）。

## 9. 风险清单

### 9.1 连接生命周期 / 半开

| 风险 | 依据 | 影响 |
|---|---|---|
| 半开很难「检测」 | TCP 没有半开探测；本仓 TCP 读有 `TCP_READ_TIMEOUT = 30 s`（`src/main.rs:110`），只作用于**控制面帧读取** | 数据连接若复用同一 helper，30 s 静默的业务流会被误杀；若不复用，静默半开要等到 keepalive/写失败才回收 |
| 双侧关闭必须联动 | RFC §5.5 三条 MUST | 任一侧 RST/EOF 后另一侧不关 → fd 泄漏 + 端口池耗尽 |
| 未 bind 的 pending 连接 | RFC §5.2/§5.3：30 s MUST 关闭 | 需要 per-connection 计时器（现有 `sweep` 是 per-allocation，`src/turn.rs:725`） |
| 预绑定缓冲 | RFC §5.2/§5.3 MUST 缓冲；§7 允许超限丢弃 | 缓冲上限是**新的**内存上限旋钮（现有配额只数 allocation，`Config` 无字节上限） |
| `Connect` 超时下限 30 s | RFC §5.2「timeout MUST be at least 30 seconds」；coturn 实测 19.4 s | 本仓若沿用 `TCP_READ_TIMEOUT` 的 30 s 只是巧合，需要**独立**常量避免耦合 |

### 9.2 资源上限

| 风险 | 依据 |
|---|---|
| **数据连接不受 allocation 配额约束** | `--max-allocations-per-user/-ip` 只数 allocation（`src/turn.rs:1077-1097`）；一个 allocation 可挂 N 条数据连接（N 无上限） |
| `--max-inflight` 按 accepted 连接计数 | `src/main.rs:2542-2559` 注释明写；每条数据连接都占一个 slot ⇒ 大文件传输会「吃掉」`--max-inflight`，与「每 datagram 并发」的直觉不同 |
| fd 消耗 | 每条数据连接 = 2 个 fd（client 侧 + peer 侧）+ 任务；`TCP_LISTEN_BACKLOG=1024`（`:111`） |
| relay 端口池 | `used_ports: HashSet<u16>` 只服务 UDP（`src/turn.rs:534`）；TCP listener 需要独立池，否则与 UDP 端口互相抢 |
| 现有配额对 TCP 同样生效（PRD 硬约束） | allocation 级天然生效；**连接级**需要新的旋钮 |

### 9.3 平台差异（Linux/macOS/Windows）

- 现有 TCP 路径无 unix-only 依赖（`libc` 只用于 `DONT-FRAGMENT`，`src/turn.rs:2328-2394`），
  `tokio::io::split` + `shutdown()` 三平台可用 ⇒ **数据面半关闭在 API 层面可移植**。
- 差异点（**未在本机验证**，标注为待验证）：Windows 上 `shutdown(SHUT_WR)` 后再读对端数据的行为、
  macOS 上 RST 的 `ConnectionResetError` 映射、以及 `SO_REUSEADDR` 在 Windows 的语义
  （`src/main.rs:3483-3486` 已有注释：「Windows 把 SO_REUSEADDR 映射成 steal the port」，故加了 `cfg(unix)` 门槛）。
- `ss` 只存在于 Linux ⇒ lab 的 `relay_listeners()` 本来就是 Linux-only，新增 TCP 断言不增加平台负担。

### 9.4 与 `--max-inflight` 的关系（明确表述）

- 现状：UDP 一个 datagram 一个 permit（`--max-inflight` 设了才 spawn），TCP **一条连接**一个 permit
  且**整条连接生命周期**持有（`src/main.rs:2544`）。
- TCP allocation 引入的每条**数据连接**都是新 accepted TCP 连接 ⇒ 同一个 `--max-inflight` 会同时限制
  「控制连接数」与「数据连接数」。若 `--max-inflight 8` + 一个客户端开 2 个 allocation × 各 4 条连接，
  单机就把全局 slot 吃满 —— 这是**语义变化**，需要在文档与 design 中明写。

### 9.5 其它

- **属性白名单**：`turn_unknown_attributes_with`（`src/turn.rs:2435-2473`）是 420 的唯一判定；
  忘加 `0x002a` 会让 `Connect` 直接 `420`。
- **`Send`/`ChannelBind` 对 TCP allocation 无意义**：需要明确返回什么（400 或忽略），否则会出现
  「TCP allocation 上 channel bind 成功但从不转发」的静默错误。
- **`-P` 验收不稳**（50% 丢包实测）。
- **文档一致性**：`docs/book/src/turn.md:35/82/159`、`README.md:22`、`CHANGELOG.md:122`、
  `.trellis/spec/backend/turn.md:42`、`src/turn/tests.rs:1083` 全部写死 442，需一并改。
- **`frozen` 字节冻结**：新增行为在**默认路径**不应出现；`REQUESTED-TRANSPORT=6` 属于显式请求，
  但若新增开关（如 `--turn-tcp-relay`），默认关闭时 17 个请求必须字节不变（`script/lab/rstun-turn.sh:1056`）。

## 12. Design 阶段必须先拍板的 3 个取舍

> 以下是**取舍项**（选项 + 代价 + 推荐），不是实现方案。

### D1：TCP 中继是「新特性开关」还是「`--turn` 下自动启用」

| 选项 | 做法 | 代价 / 风险 |
|---|---|---|
| A. 新开关 `--turn-tcp-relay`（默认关） | 不加开关时 `REQUESTED-TRANSPORT=6` 继续 442 | 默认路径字节完全不变（最容易过 `frozen` + 「默认 442 不变」的 PRD 硬约束）；代价是多一个 flag、多一组「开关 × 4 传输」测试矩阵 |
| B. `--turn` 下自动启用 | 442 分支直接变成成功路径 | 少一个开关；代价是「默认构建不静默改变语义」这条 PRD 约束被打破（442 → 200 是行为变化），需要明确写进 CHANGELOG 与行为表 |
| **推荐** | **A** | PRD 硬约束写了「现有 442 行为在未启用特征时保持不变（即默认构建不静默改变语义）」——A 是唯一能直接满足它的形态 |

### D2：本期是否包含被动模式（`ConnectionAttempt`）

| 选项 | 做法 | 代价 / 风险 |
|---|---|---|
| A. 只做出站（`Connect` + `ConnectionBind`） | 不做 `0x00c`、不做 accept 循环、不做 `ConnectionAttempt` 反向推送 | 覆盖 PRD 的主用例（UDP 被阻断的企业网）；少一套「allocation → 控制连接」反向通道；`uclient -T` 已能验证 |
| B. 出站 + 被动一次做完 | 加 `0x00c` + accept 循环 + 30 s bind 计时器 | 多一条反向控制通道（UDP/TCP/TLS/DTLS 四种 sink 都要覆盖）；验收判据不稳（`-P` 实测 50% 丢包，不能复用 `uclient_ok`） |
| **推荐** | **A**（被动模式另开任务，作为 RFC 6062 的第二个子项） | 理由见 §5.4：两者共享 `CONNECTION-ID` 表与 bind 状态机，只差「谁发起」，先做主动不会造成返工 |

### D3：`CONNECTION-ID` 与数据连接的状态归属

| 选项 | 做法 | 代价 / 风险 |
|---|---|---|
| A. 独立全局表 `HashMap<u32, PendingConnection>` + `Allocation` 内只存 id 集合 | 数据连接不参与 `Key` 5 元组；pending 连接由 `sweep` 统一回收 | 与现有「allocation 表 + 1 s sweep」一致；代价：`sweep` 要管两/三类 TTL，且 `release_connection` 要级联关闭 |
| B. 把数据连接塞进 `Allocation.state`（`AllocationState` 里加 `connections: HashMap<u32, ...>`） | 状态集中 | 连接对象含 `TcpStream`/task handle，`AllocationState` 现在被 relay reader 以 `RwLock` 高频读写（`src/turn.rs:2109-2131`），会引入锁竞争；且 `AllocationState` 是 `Copy`-less 但被 clone 读 |
| C. 每数据连接一个独立 task，自己管生命周期，只把 id 注册到全局表 | 与 `spawn_relay_reader` 同构 | 回收要靠「表里没有 → task 自杀」或 channel 通知；`LIFETIME=0`/过期时的级联关闭要显式做 |
| **推荐** | **A + C 的组合**（全局 id 表为真源，连接本体在独立 task 里，sweep 只负责按 deadline 摘表并 abort） | 与现有 `Allocation`/`relay_task` 模式一致（`Drop` abort），不污染数据面锁 |

另需一并拍板（不计入 3 个，但会阻塞实现）：
- `LIFETIME=0` 时**控制连接**是否关闭（coturn 关；本仓现状 UDP 版不关）；
- TCP allocation 上收到 `Send`/`ChannelBind` 的响应（400 还是静默忽略）；
- 数据连接是否计入 `--max-inflight`（现状必然计入，因为它是 accepted 连接 —— 需要决定是否**绕过**）。
